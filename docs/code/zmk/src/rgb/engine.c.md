# zmk/src/rgb/engine.c

The per-key backlight. Replaces ZMK's single-colour underglow in builds whose keymap has a `crush80,rgb-scheme` node (`build.sh` then adds `conf/rgb-engine.conf`: underglow off, `LED_STRIP` on; otherwise `conf/rgb-underglow.conf`). One owner of the strip, so the two never run together.

**Event driven, no tick.** Layer, position, modifier, activity, endpoint and USB events call `request_render()` (5 ms coalescing, on a private work queue, 1.5 KB stack, priority 5). A frame is built, scaled, compared with the last one, and only then sent to the driver (`led_strip_update_rgb`, 154 pixels, one DMA transfer). All black means the driver cuts the LED supply (PC2). ZMK's underglow, by contrast, woke the CPU 20 times a second for as long as it was "on".

**What is lit.**
- LEDs 92-153 (side bar and logo): the colour of the highest active layer that is not a marker layer (`layer-modes` = 2). The Windows list (`layer-side-win`) is used while the Win layer is active. 0 = dark.
- Keys (LEDs 0-91 through `led_map_data.h`): for each position the binding in force is found by walking the active layers from the top and skipping `transparent`. `none` stays dark. Otherwise `classify()` maps the binding to one of 18 groups by behaviour name and HID usage (arrows, line, word, page, delete, clipboard, numbers, symbols, plain keys, macros, layer keys, modifiers, Esc/Tab/Enter/Space, F-keys, media, desktop, system, bootloader), and the colour comes from `group-colors`. `overrides` (layer, position, colour) win over the group colour. Layer mode 0 keeps all keys dark (Base, Native).
- A home-row-mod key whose hold modifier is currently held (`zmk_hid_get_explicit_mods()`) lights only itself in `mod-colors`, on every layer; a plain modifier key additionally needs its pressed bit. Position events do not reliably reach the engine (the keymap listener can consume them first; confirmed on the board 2026-11-20, the first fix lit nothing), so home-row keys are recognised by held state alone. Each home-row key has a distinct modifier usage, so exactly one lights. A tap never lights. Side effect: holding a physical Left Ctrl also lights `A`. The redraw is triggered by `zmk_keycode_state_changed` (a hold resolving presses `&kp LCTRL` etc.); ZMK never raises `zmk_modifiers_state_changed`, which is why the first overnight build did not light held mods (found on the board 2026-11-20).
- `tools/gen_docs.py` in the private keybindings repo holds a Python port of `classify()` to draw the colour legends; keep the two in step.

**Policy.** Idle (`ZMK_ACTIVITY_*` not active): off. Output Bluetooth: off unless toggled (`ble_on`, never saved); USB: `st.enabled` (saved). Brightness is 10 levels of `CRUSH80_RGB_BRT_MAX` percent (25); a frame whose channel sum exceeds `CRUSH80_RGB_BUDGET` (30000) is scaled down, whatever the colours. State is saved as `c80rgb/state` 3 s after a change; idle and Bluetooth state are never saved.

**Failure.** A failed strip update retries after 200 ms, twice; after 10 failures in a row the engine stays dark until reboot. The strip driver already turns a stuck DMA into "LEDs off" (`led_strip_b91_spi.c`). No `irq_lock` in this file.

**Not verified.** Compiled in CI; **not yet run on the board** (status.md). Unknown until then: whether the LED order (`led_map_data.h`, from upstream's stock-firmware table, re-keyed by matrix position) matches this board, which LEDs of 92-153 are side bar versus logo (all 62 get the same colour), whether the Bluetooth/USB endpoint reading is right with `ZMK_USB_NO_VBUS_DETECT`, and the hold-tap versus position-event ordering for the held-modifier light.
