# zmk/src/rgb/engine.c

The per-key backlight. Replaces ZMK's single-colour underglow in builds whose keymap has a `crush80,rgb-scheme` node (`build.sh` then adds `conf/rgb-engine.conf`: underglow off, `LED_STRIP` on; otherwise `conf/rgb-underglow.conf`). One owner of the strip, so the two never run together.

**Event driven; one tick, only while visible.** Layer, position, modifier, activity, USB and battery events call `request_render()` (5 ms coalescing, on a private work queue, 1.5 KB stack, priority 5). A frame is built, scaled, compared with the last one, and only then sent to the driver (`led_strip_update_rgb`, 154 pixels, one DMA transfer). All black means the driver cuts the LED supply (PC2). The only periodic work is the ambient animation (below): `render_handler` reschedules itself every 40 ms only when the frame it just built was ambient, so the tick stops by itself on the first frame that is not (battery, backlight off, idle, another layer). ZMK's underglow, by contrast, woke the CPU 20 times a second for as long as it was "on".

**What is lit.**
- LEDs 92-153 (side bar and logo): the colour of the highest active layer that is not a marker layer (`layer-modes` = 2). The Windows list (`layer-side-win`) is used while the Win layer is active. 0 = dark.
- Keys (LEDs 0-91 through `led_map_data.h`): for each position the binding in force is found by walking the active layers from the top and skipping `transparent`. `none` stays dark. Otherwise `classify()` maps the binding to one of 18 groups by behaviour name and HID usage (arrows, line, word, page, delete, clipboard, numbers, symbols, plain keys, macros, layer keys, modifiers, Esc/Tab/Enter/Space, F-keys, media, desktop, system, bootloader), and the colour comes from `group-colors`. `overrides` (layer, position, colour) win over the group colour. Layer mode 0 keeps all keys dark (Native).
- **Ambient (layer mode 3, Base).** While a USB host has configured the board and the bus is not suspended (`zmk_usb_is_hid_ready()` and status not `USB_DC_SUSPEND`), every key LED and LEDs 92-153 show a two-colour wave (`ambient-colors`, or `ambient-colors-win` while the Win layer is active; optional properties, defaults in `engine.c`). The maths is in `effects.h` (host-tested by `scripts/tests/test_rgb_effects.py`): eased triangle wave, x from the matrix column, y from the row; macOS runs left to right in 6 s, Windows right to left, tilted by row, in 8 s. LEDs 92-153 get x by index because their geometry is unmapped. Without a host the layer behaves like mode 0 and its `layer-side` colour (0 on Base), so the board is dark and PC2 is cut. This is the only cable signal the board has (no VBUS pin). A pulled cable leaves the status at SUSPEND, and ZMK still calls that "HID ready" (`ZMK_USB_SUSPEND_REATTACH` is off in these builds, so nothing drops it), hence the explicit SUSPEND check. A sleeping host also suspends the bus, so the wave stops then too. Read from `usb.c` and patch 0001, not yet seen on the board. Held-mod lights draw over the wave.
- **Battery gauge (`&c80rgb_bat`, action 3).** While held, the frame is only the number row: `c80_gauge_keys()` keys from 1 (one per full 10 %, at least one, all ten at 100 %), coloured red to green by position, at full level of the 25 % cap. It ignores on/off, idle and the output. Positions are found by matrix row 1, columns 1-10. The reading is ZMK's last battery sample (every 60 s, linear voltage, `features/battery.md`); while charging it reads high. The behaviour's release clears it (`c80_rgb_release()`); ZMK delivers the release to the behaviour that took the press, whatever the layer is by then. A 10 s timeout also clears it, so a lost release cannot keep LEDs lit on battery (the gauge overrides idle and off).
- A home-row-mod key whose hold modifier is currently held (`zmk_hid_get_explicit_mods()`) lights only itself in `mod-colors`, on every layer; a plain modifier key additionally needs its pressed bit. Position events do not reliably reach the engine (the keymap listener can consume them first; confirmed on the board 2026-11-20, the first fix lit nothing), so home-row keys are recognised by held state. Two home-row keys can share a modifier (left-hand and right-hand mods both send left modifiers since 2026-11-20): `pick_home_row_mods()` lights only the one whose pressed bit is set when exactly one is, and every key of that modifier otherwise (the fallback when position events do not arrive). Not yet seen on the board. A tap never lights. Side effect: holding a physical Left Ctrl also lights `A`. The redraw is triggered by `zmk_keycode_state_changed` (a hold resolving presses `&kp LCTRL` etc.); ZMK never raises `zmk_modifiers_state_changed`, which is why the first overnight build did not light held mods (found on the board 2026-11-20).
- `tools/gen_docs.py` in the private keybindings repo holds a Python port of `classify()` to draw the colour legends; keep the two in step.

**Policy.** Idle (`ZMK_ACTIVITY_*` not active): off. On battery (no active USB host, same test as the ambient wave), a top layer of mode 0 or 3 (Native, Base) is fully dark: no side bar, no held-mod light, so typing on Base never powers the LED rail. Otherwise `st.enabled` (saved), on USB and Bluetooth alike (`decisions/rgb.md`, 2026-11-20 evening); the old Bluetooth-only flag was never saved, so the settings layout is unchanged. Brightness is 10 levels of `CRUSH80_RGB_BRT_MAX` percent (25); a frame whose channel sum exceeds `CRUSH80_RGB_BUDGET` (30000) is scaled down, whatever the colours. State is saved as `c80rgb/state` 3 s after a change; idle and Bluetooth state are never saved.

**Failure.** A failed strip update retries after 200 ms, twice; after 10 failures in a row the engine stays dark until reboot. The strip driver already turns a stuck DMA into "LEDs off" (`led_strip_b91_spi.c`). No `irq_lock` in this file.

**Not verified.** Compiled in CI; **not yet run on the board** (status.md). Unknown until then: whether the LED order (`led_map_data.h`, from upstream's stock-firmware table, re-keyed by matrix position) matches this board, which LEDs of 92-153 are side bar versus logo (all 62 get the same colour), whether `zmk_usb_is_hid_ready()` falls after a cable pull (ambient off on battery), whether the LED supply works on battery at all, and the hold-tap versus position-event ordering for the held-modifier light.
